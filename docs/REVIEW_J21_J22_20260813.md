## 1. What the journals are for

J21's goal (from README + docstring): measure the rolled-up mass and surface
area of every BoM-visible 3D master in an open NX 2506 assembly and persist
`NX_MassPropRollupMass` (kg) / `NX_MassPropRollupArea` (mm^2) on each part,
reporting what NX wrote (read-back), with DRY_RUN / SMOKE / PROBE modes.

J22 is a fast one-part diagnostic: on the active work part it tests (A) the
classic measure APIs, (B) the native mass-properties builder, (C) direct
attribute writes per category, and dumps before/after attributes — to decide
which write mechanism works on this NX build.

## 2. The technical story the evidence tells (important)

The commit history and logs show two full direction changes:

1. **Direct-write approach (abandoned).** `docs/NX2506_J21_J22_RESERVED_LOG.md`
   documents an APPLY run of the older V4 build: 15/15 parts
   `WRITE_FAILED` with **"This is a reserved attribute title. [512006]"** for
   both `NX_MassPropRollupMass` and `NX_MassPropRollupArea` in both
   "Rolled-Up Mass Properties" and "Materials" categories. The journal's
   AttributePropertiesBuilder writes were rejected by NX — these titles are
   reserved and only NX's own mass-properties update may populate them.

2. **Native update approach (current, correct direction).** `bc2f4cb` reverted
   J21 to drive NX's native mass-properties update
   (`PropertiesManager.CreateMassPropertiesBuilder` with
   `UpdateOnSave=Yes`, then `UpdateNow` + `Commit`) instead of writing
   attributes directly. The current docstring documents exactly why. This is
   the right mechanism — confirmed independently by J22's diagnostic:
   `C_direct_write` fails with [512006] on every category, while
   `B_native_builder` runs OK.

**So the current J21 direction is technically sound** — it stopped trying to
write reserved attributes and instead triggers the mechanism NX itself uses.

## 3. Findings

### [HIGH] J21 has no committed proof that the native update populates the attributes end-to-end

- `docs/NX2506_J21_SMOKE_LOG.md` (current V3 build, SMOKE mode, 1 part):
  `264MN032797A01 | 0 | rollup mass=<blank> kg [BLANK] | rollup area=<blank> m^2 [BLANK] | saved=SAVED | PARTIAL`
  — i.e. even the native update left the attributes blank on the work part.
- The J22 diagnostic explains why this is not yet conclusive: the SMOKE run
  measured the **assembly work part** `264MN032797A01`, which has **0 solid
  bodies** (`solid_body_count: 0`, `A_classic_compute -> NO_SOLID_BODIES`),
  and the roll-up attributes live on **child component parts**, not the empty
  assembly part. `29cc233` added child read-back to J22 precisely for this
  reason.
- **Gap:** no committed APPLY-mode run (or J22 run with the child read-back)
  yet shows a single non-blank `NX_MassPropRollup*` value. Until one does,
  the journal's headline claim ("NX writes the standard attributes on every
  component") is unproven on this build.
- **Fix:** run J21 in APPLY mode (or J22 with the current `29cc233` code) on
  the full assembly and commit the CSV/JSON showing ≥1 populated child part.

### [MEDIUM] README.md row 21 is stale — still describes the abandoned direct-write mechanism

- `README.md` line 64 says J21 "Measures roll-up area + mass with the classic
  NX measure APIs and **writes** `NX_MassPropRollupArea` /
  `NX_MassPropRollupMass` … (standard category with `Materials` fallback)".
- That is the abandoned V4 behavior. Current code (V3) does **not** write
  attributes at all — it triggers the native update. `from_git/README.md`
  lines 47–54 already describe the native mechanism correctly, so the two
  READMEs contradict each other.
- **Fix:** update `README.md` row 21 to match `from_git/README.md` wording.

### [MEDIUM] J22 committed JSON predates the child read-back fix

- `J22_DIAGNOSTIC_264MN032797A01_20260813_004652.json` (committed `dcfd602`)
  shows `B_native_read_back: BLANK` with only work-part values
  (`NX_MassPropRollupMass_kg: null`, `NX_MassPropRollupArea_mm2: null`) and
  **no `children` array** — because the read-back at that time only checked
  the work part.
- `29cc233` (later) added child-part read-back and assembly-builder probes so
  "the next J22 run [is] definitive about whether NX's native update writes
  the reserved roll-up attributes" — but **that run's output is not committed**.
- **Fix:** run J22 with the current code and commit the fresh JSON/CSV.

### [LOW] SMOKE log says PARTIAL — fine as an honest artifact, but easy to misread

- The SMOKE log is honest (the mechanism did not populate the empty assembly
  work part), and the docstring already notes SMOKE reports NO_SOLIDS on
  assembly parts with no own bodies. Consider adding one clarifying line to
  the smoke log that a BLANK result on an assembly work part is expected and
  that the roll-up lives on children (APPLY mode proves it).

### [LOW] Reserved log should state it documents the abandoned approach

- `docs/NX2506_J21_J22_RESERVED_LOG.md` is titled "J21 … + J22" and shows the
  old direct-write build (V4, "classic measure APIs + AttributePropertiesBuilder
  write"). It is valuable evidence of *why* the mechanism changed, but the
  header doesn't say it is the superseded build. One sentence ("superseded by
  V3 native-update build") would prevent confusion.

### [INFO] `documents/` is untracked (15 MB NXOpen Intellisense reference)

- `documents/input/` contains the NX12 Intellisense API stubs (auto-generated
  reference), `Att-264MN021145A01_20Apr26.xlsx`, and
  `nx_teamcenter_attribute_mapping_cross_checked.json`. It is not tracked and
  not mentioned in README. This looks like local reference material, not a
  journal deliverable — leaving it untracked is reasonable. If the attribute
  mapping JSON is meant to be shared, commit just that file (not the 15 MB
  stubs).

## 4. What is good

- **Correct mechanism decision:** after evidence (reserved-title errors), the
  journals correctly stopped direct-writing reserved attributes and moved to
  the native builder. J22's category testing (Rolled-Up Mass Properties vs
  Materials) is exactly the right experiment.
- **Honest evidence:** the logs report BLANK/PARTIAL rather than fabricating
  success; the JSON dump is a faithful before/after attribute landscape.
- **Self-contained deployment:** no third-party deps, Desktop-based IO with
  `NX_JOURNALS_IO_DIR` override, safe `_text`/`clean`/`error_text` helpers.
- **Tests:** 15 unit tests pass (`pytest tests/ -q` → 15 passed), covering
  APPLY/SMOKE/DRY_RUN/PROBE modes, BOM-visibility filtering, blank
  reporting, save-failure continuation, and a source-level guard
  (`test_native_only_no_manual_compute_or_attribute_write`) that the journal
  does not call `NewFaceProperties`/`NewMassProperties`/
  `CreateAttributePropertiesBuilder`/`SetRealAttribute` — i.e. it enforces
  the native-only contract.
- **Defensive traversal:** suppression/reference/keyword filtering mirrors
  NXOpenBoMExtended; manager fallback (PropertiesManager → MeasureManager)
  and instance-resolved UpdateOptions handle build differences.
